# v0.2.0 Readiness

The honest status of ThreeM at the commit that cuts v0.2.0, written to be read
by somebody deciding whether to push the tag. Every figure below is a
measurement with a command behind it. Where something was not measured, this
says so instead of rounding it up to a claim.

**Verdict: ready to tag, with three live defects a user can reach and one
safety feature that does not do its job.** None of them destroys data. One of
them — a zero-byte `.jpg` — crashes a *preview*, which is the posture the whole
release is built on. They are listed in [Live defects](#live-defects) before
anything else, because a readiness report that opens with its coverage
percentage is selling.

## Live defects

Three things in this release are wrong today. All three were reproduced against
this commit while writing this report, not carried forward from a note.

### 1. A zero- or one-byte image file panics the process, in dry run

```console
$ printf 'a' > one.jpg ; : > zero.jpg
$ mmm . --no-config
Planning file organisation...
thread 'main' panicked at nom-exif-1.5.2/src/jpeg.rs:110:5:
assertion failed: input.len() >= 2
$ echo $?
101
```

A file under two bytes with an image extension takes the whole run down inside
the dependency, during **planning** — so `--commit` is irrelevant and the safe
posture does not protect anybody from it. A truncated download or an interrupted
copy in a library is enough to produce one. The user sees a Rust panic, no
summary, and no indication which file did it.

The fix is in the planner, not the dependency: treat a file the metadata layer
cannot even attempt as undated rather than fatal. It was found in Phase 03 and
carried, untouched, through every phase since — recorded each time and never
scheduled. Two bytes is the exact boundary: a two-byte file reports
`format not supported` and the run completes.

**This is the first thing v0.2.1 should fix.**

> **Fixed in 0.2.1.** `metadata::extract_metadata` now answers a file too short
> to hold a container signature before any parser sees it. Two details above are
> wrong, and were measured while fixing it: a **zero-byte file never panicked**
> (the parser refused it before reaching the assertion, so the boundary is
> exactly one byte), and the defect was **not confined to image extensions** —
> `.mov` and `.mp4` aborted at the same assertion, because the probe runs before
> the container is identified. This report is left as it stood at the 0.2.0 tag;
> the correction lives here rather than in the text above it.

### 2. `mmm-dedup-verifier` confirms nothing and exits 0

The independent second opinion — the tool a user runs before deleting a
`duplicates/` directory — verifies nothing on a tree `mmm` itself produced.
`move_duplicates` writes the manifest *before* the organise pass, so every
`# Original kept at:` path points at the file's **input** location, which the
organise pass then empties. The verifier resolves that path, finds nothing,
records `OriginalMissing`, confirms **zero** groups, prints *"All verified
groups are confirmed duplicates"* and **exits 0**.

Only `--check-originals` turns it into a failure. Pinned by
`tests/dedup.rs::the_manifest_records_input_paths_which_go_stale_when_the_run_moves_them`,
which is written to fail loudly if the manifest is ever fixed — so the suite
being green is confirmation the defect is still live, not evidence against it.

Found in Phase 01. The fix — rewrite the manifest with final destinations after
the organise pass, and make a zero-confirmed run non-successful — is a product
change that was never scheduled.

> **Fixed after the 0.2.1 tag.** The organise pass now appends
> `# Original moved to:` to each manifest once the retained original has landed,
> and the verifier prefers that line — appending rather than rewriting the
> header, so the crash-safety the manifest was built for is unaffected. A run
> that confirms nothing now exits 1, whether the originals are missing or the
> groups carry no manifest. Phase 07 fixed the verifier's *labels* (it
claimed SHA-256 while computing BLAKE3) and gave it its first tests, but did not
touch this.

### 3. A photograph with GPS and no readable date loses its coordinates

The undated `FileMetadata` carrying the coordinates is discarded in favour of
the filesystem timestamp, taking the location with it, so the file is named
without its location suffix. Found in Phase 05 and left: restoring it changes
output filenames, which is its own change with its own changelog entry.

> **Fixed after the 0.2.1 tag.** `Extracted::Undated` now carries the
> coordinates the file recorded, and `extract_metadata` attaches them to the
> filesystem-fallback answer. Such files gain a location suffix; nothing already
> organised is renamed.

## What shipped

v0.2.0 is the release that gives ThreeM a safety model. 0.1.0 reorganised a
library in place on a bare `mmm ~/Photos` — no preview, no record, no way back.

| Area | What it is now |
|---|---|
| **Posture** | Preview by default. `--commit` is the only thing that moves a file, and cannot be set from a config file or an environment variable. |
| **Moves** | `link()` + `unlink()`, which refuses an occupied name including a dangling symlink. No `rename()` overwrite anywhere on the path. |
| **Cross-volume** | Copy, `sync_all`, compare BLAKE3 digests, *then* delete the source. The old size-only check passed a corrupt copy. |
| **Journal** | Append-only JSONL, one intent line fsynced before each move and one outcome line after. Survives truncation. |
| **Undo** | `mmm undo` replays in reverse, verifies each file before touching it, reports four outcomes, and is itself journalled. |
| **Timezones** | An EXIF timestamp is a local wall clock, not a UTC instant. Directory and filename come from the digits the camera wrote, on every machine. |
| **Formats** | Verified per family by fixture. RAW cannot be read by the parser at all and now says so instead of silently taking the filesystem date. |
| **Sidecars** | `.xmp` / `.aae` / `.thm` travel with their parent under both naming conventions, and an `.xmp` can *supply* a date — the only route by which a RAW library gets a real one. |
| **Configuration** | Thirteen keys over four layers, every one wired, with `mmm config show` naming the layer each value came from. |
| **Dedup** | Deterministic grouping, parallel hashing on a run-owned pool capped at 8 threads, small files settled without a second read. |

Three changes break something for an existing user: preview by default, the
timezone-corrected output paths, and the flat `YYYY-MM-DD/` date tree. None
migrates an existing library. `docs/USER-GUIDE.md` § Upgrading from 0.1.0 states
what to do instead.

## The gate, as measured at this commit

```console
$ cargo fmt --check                              # exit 0
$ cargo clippy --all-targets -- -D warnings      # exit 0
$ cargo test --all-targets                       # 630 passed, 0 failed, 0 ignored
$ cargo build --release                          # exit 0
$ cargo package --allow-dirty                    # 43 files, verify build clean
```

630 tests across sixteen targets, from 25 at the start of the playbook. The
scenario test is ~22 s of a ~35 s integration run.

CI runs five jobs on `push` and `pull_request`: `test` and `release-build` over
`ubuntu-latest` × `macos-latest`, plus `msrv`, `coverage` and `fuzz` on Linux
only. MSRV is **1.87.0**, measured rather than asserted — the library and both
binaries compile on 1.86, but `tests/common/mod.rs` uses `is_multiple_of`, so
1.87 is the floor for anything that has to pass the gate.

- **The verifier's 0% is stale, and nothing has re-measured it.** The report

  binary is read-only and cannot lose data, which is why it was outside the
  original bar.
- **Two lines are unreachable by construction** — `organiser.rs:595` (a total
  match arm) and `sidecar.rs:272` (an `if let` whose `None` cannot occur) — and
  five `main.rs` sites need an open descriptor to fail mid-write or a file to
  vanish between the scan and the plan. All are commented at the site and listed
  in the report with a reason.

## Mutation testing

`cargo-mutants` 27.1.0, scoped to the four modules that decide what moves and
what is recorded: `organiser.rs`, `journal.rs`, `hasher.rs`, `metadata.rs`. 313
mutants, roughly an hour at `-j 4`. Full detail in [[mutation-testing]].

| | Baseline | After |
|---|---:|---:|
| Mutants generated | 313 | 313 |
| Caught | 246 | **257** |
| **Missed** | **19** | **8** |
| Unviable (did not compile) | 47 | 47 |
| Timeout | 1 | 1 |
| **Mutation score** (caught ÷ viable) | 92.83% | **96.98%** |

Nineteen changes to those modules could be made without any of 603 tests
failing. Eleven were real gaps and are closed; six tests were added, 603 → 609.

**Two of the eleven would have moved files to the wrong place**: deleting the
`EntryValue::Text` arm from `entry_to_wall_clock` or `entry_to_reading` (fires
only for cameras that spell the tag their own way, so no fixture reached it),
and replacing `reading_year` with a constant, which lets a negative EXIF year
through to produce a `-44-03-15` directory.

Eight survivors are accepted, each reasoned in the report: a read-buffer length,
a counter read only by a `debug!`, two guards unreachable by construction, the
video `"CreateDate" | "DateTimeOriginal"` arm (measured dead against `nom-exif`
1.x by probing every video fixture, not assumed), two `ChunkController` default
bodies the mutation leaves semantically identical, and one timeout the suite
detects by hanging.

**The gaps this leaves are real.** `undo.rs` and `sidecar.rs` were outside the
four modules and **have not been mutated at all** — both are destructive
surfaces by this project's own standard. And there is no CI gate: an hour a run
is too slow for a pull request, `--in-diff` mode was not evaluated, so nothing
stops a new surviving mutant appearing.

## Fuzzing

Four `cargo-fuzz` targets over the parsers that read bytes somebody else wrote,
under AddressSanitizer. ~29.6 million executions. Full detail in [[fuzzing]].

| Target | Duration | Executions | Crashes |
|---|---:|---:|---:|
| `parse_iso6709` (before the fix) | 3 s | 164 | **1** |
| `parse_iso6709` (after) | 181 s | 9,772,769 | 0 |
| `parse_wall_clock` | 181 s | 8,088,221 | 0 |
| `journal_line` | 181 s | 6,831,584 | 0 |
| `xmp_sidecar` | 241 s | 4,948,246 | 0 |

**One defect, found after 164 executions: `-33.8688+302.2093/`.** `f64::from_str`
accepts `NaN`, `inf` and any magnitude, and `geocoder::lookup` rejects none of
them — measured, a `NaN` coordinate returns the *first record in the GeoNames
dataset*, so a video with a corrupt location tag was filed and renamed after
Andorra with nothing to say the place was invented. Now refused against ISO
6709's own bounds; the crashing input is checked in as a regression seed.

**The task's predicted UTF-8 panic is not real.** Every offset sliced is the
position of a `+` or `-`, and an ASCII byte cannot occur inside a multi-byte
UTF-8 sequence, so all slices are char boundaries by construction. 17M
executions over multi-byte input agree.

**Nothing runs long.** Longest run 4 minutes, CI gate 60 s per target. No
scheduled campaign exists, and the defects a multi-hour campaign finds are
exactly the ones needing deep structured input. Three parsers have no target at
all: the TOML settings loader, `undo.rs`, and `Journal::read`'s multi-line
framing. The corpus is 3–6 hand-written seeds per target with no structure-aware
fuzzing, and `xmp_sidecar` never saw an input above libFuzzer's default 4 KB
ceiling — smaller than a real Lightroom sidecar.

**The fuzz crate is pinned to `nightly-2026-05-01`.** Current nightly does not
compile `nom-exif` 1.5.2 at all (`std::range::Range` vs `std::ops::Range`), a
dependency problem unrelated to fuzzing. The unpin condition is in
`code/fuzz/README.md`.

## Hashing throughput

Criterion, same machine (8-core M1 Pro), same OS build, same rustc, same corpus,
same sampling as the serial baseline — verified rather than assumed, because a
baseline is only a baseline if one variable changed. Full detail in
[[hashing-baseline]].

| Measurement | Serial | Parallel | Speedup |
|---|---:|---:|---:|
| Whole cascade (`mixed`) | 102.49 ms | 38.652 ms | **2.65×** |
| Phase 3 (full hash) | 94.347 ms | 38.687 ms | **2.44×** |
| Phase 2 (partial hash) | 3.6495 ms | 1.2868 ms | **2.84×** |
| Tier `medium_5m` | 15.471 ms | 5.2276 ms | **2.96×** |
| Tier `large_50m` | 73.179 ms | 36.180 ms | **2.02×** |
| Tier `small_100k` | 2.7948 ms | 1.6847 ms | see below |

Separately, the small-file promotion (a file the partial hash already read
whole is not read again): a 250 MB tree of 6,400 duplicate 40 KB files went
**0.61 s → 0.52 s**, with phase 3 going from 6,400 reads to zero. The benchmark
corpus cannot see this — every tier is ≥100 KB — so it was measured directly
against the workload it is for.

**Three caveats, and the third is a correction to a published number.**

- **Everything is page-cache-warm.** Criterion re-runs over the same corpus, so
  these numbers measure BLAKE3 plus syscalls, not cold disk. Every speedup here
  is an **upper bound** on what a user with a cold library sees.
- **Phase 1's apparent 1.61× is noise, not a win.** Its function body is
  byte-for-byte identical to the baseline commit. The serial interval spanned
  48%; the honest reading is that the old number was unreliable.
- **`small_100k`'s published 1.96× was the luckiest of five runs and is not
  quotable.** Five measurements of a byte-for-byte identical binary spanned
  1.42–2.27 ms, with criterion reporting a statistically significant improvement
  *and* a statistically significant regression among them. The tier is 48 files
  finishing in under 2 ms, short enough that one scheduling hiccup dominates.
  **The defensible figure is between 1.2× and 2.0×.** Everything else
  reproduced: `large_50m` within 0.3%, `mixed` within 1.3%.

## Format families that could not be verified

The support matrix covers 32 extensions. `nom-exif` 1.5.2 recognises exactly
four containers — JPEG, HEIF, QuickTime, MP4 — which is the measured fact behind
most of the table. Three cells are genuinely unknown, and eleven more are
derived rather than measured.

| Family / capability | Why it is unverified |
|---|---|
| `.cr3` date **and** GPS | No fixture. Canon stores EXIF in a custom `CMT1` box, so the EXIF date almost certainly will not read — but a CR3's compatible brand `isom` *is* in the parser's MP4 brand list, so it may be taken for an MP4 and dated from `moov/mvhd`: not the shutter date, but a date, filed with no "unsupported" tag. Reading the parser cannot settle which; only a fixture can. |
| MP4 GPS via the Android `moov/udta/©xyz` atom | No fixture. `udta` and `©xyz` appear nowhere in the repository; the harness writes the *Apple* ISO 6709 key, a different path through the parser. |
| GPS in a `.3gp` | No assertion. Date extraction is verified for `.3gp`; the ISO 6709 assertion lives in the Apple `.mov` test alone. |

**Eleven ❌ rows are derived, not measured** — PNG, WebP, BMP, TIFF, AVI, MKV,
WebM, WMV, FLV, MTS and M2TS have no fixture. Their ❌ follows soundly from the
four-variant fact above, and eleven fixtures to restate it would not be worth
the maintenance. What the missing fixtures *would* catch is a container being
**mis-recognised** rather than unrecognised — which is precisely the `.cr3` case.

Two further format limits are known and live:

- **RAW dates come only from a sidecar.** No TIFF-based RAW (`.cr2`, `.dng`,
  `.nef`, `.arw`, …) can be dated from the file itself. An `.xmp` beside it
  works, and for RAW that is the normal case, but a RAW library with no sidecars
  gets filesystem dates and an `[FS: UNSUPPORTED]` tag on every file.
- **An Apple `creationdate` of exactly `+00:00` is read as an instant.** The
  parser hands it over indistinguishably from the container's `mvhd` clock,
  which is always `+00:00`, so only a non-zero offset proves the file wrote it.
  A video shot in the UTC zone can still lose its wall clock when the run's zone
  is not UTC.

## Known limitations

Everything below is true of the commit being tagged. Grouped by what it costs a
user, not by which phase found it.

### Safety and correctness

- The three [live defects](#live-defects) above.
- **`TimezoneSource::GpsDerived` is declared and nothing produces it.**
  Coordinates → zone needs a boundary database, a multi-megabyte dependency the
  resolution order does not require.
- **The dry run does not preview collision suffixes.** Two files planning to one
  destination both print the same target; the committing run produces `…-1`.
- **Duplicate relocations are not previewed at all.** They are reported by
  `print_duplicates`, not planned as `PlannedMove`s, so a preview genuinely does
  not tell you where a duplicate will land. Their journalling and reversal are
  proved; the preview gap is a real gap in the tool.
- **`unsorted/` is unreachable through the CLI except via `--require-exif`.**
  Every file on disk has a filesystem timestamp, so an undateable photograph is
  filed under the date it was *written* — which on a restored library is the
  date of the copy. Whether that is the right product decision remains open.
- **`.mmm/journal` is the only record.** Delete the output tree's `.mmm/` and
  the run is unreversible; nothing warns before that happens.

### Platform

- **Windows has never been compiled, let alone run.** `organiser::errno` is
  `cfg`-split for Linux and macOS only. A Windows `PermissionDenied` meaning "no
  hard links" would classify `Fatal` and refuse the move — the safe direction,
  and unverified.
- **CI runs UTC only.** Phases 01–07 swept `UTC` / `Asia/Singapore` /
  `America/New_York` / `Pacific/Kiritimati` by hand, and `nom-exif`'s
  local-timezone behaviour is the most likely source of a machine-dependent
  failure in this crate. No timezone leg was ever added to the matrix, so that
  regression guard is **not** protected by CI. Confirmed absent from `ci.yml`
  while writing this.
- **`msrv`, `coverage` and `fuzz` run on `ubuntu-latest` only.** A macOS-only
  MSRV break would not be caught until somebody's local build failed.
- **CI does not pass `--locked`.** A dependency edit that leaves `Cargo.lock`
  stale is silently updated in-runner rather than failing.

### Release and packaging

- **The release workflow has never run.** Its parts are individually verified —
  both scripts dry-run in both directions, the YAML parsed, four injections
  caught — but the wiring between jobs is validated by reasoning, not execution.
  The first real tag is the first real run.
- **Two of the three published binaries are never executed before publication.**
  `x86_64-apple-darwin` is cross-compiled on an arm64 runner;
  `x86_64-unknown-linux-gnu` was only ever type-checked locally, because macOS
  has no cross linker for it.
- **Nothing is signed or notarised.** macOS will quarantine a downloaded binary
  until the user clears it by hand. The checksums prove the file arrived intact,
  not who built it.
- **No draft step and no `workflow_dispatch`.** The release is public the moment
  the tag lands, and `gh release create` is not idempotent — recovering from a
  re-run means deleting the release by hand.
- **glibc, not musl.** The Linux archive will not run on an older distribution.
  No static target and no Windows target at all.
- **`keywords` and `categories` are unvalidated.** Slugs were taken from the
  crates.io list by hand; `cargo publish --dry-run` was not run, because the
  crate is not published and that path talks to the registry.
- **The `[Unreleased]` changelog link 404s** until the tag is pushed. Standard
  Keep a Changelog form; dead in the repository as it stands.
- **There is no `## [0.1.0]` section and none was invented.** 0.1.0 predates the
  changelog and was never tagged.
- **`forgejo/main` is 66 commits behind `origin/main`** and has been stale since
  before this playbook. Syncing it is a maintainer decision.

### Process

- **Nothing enforces the failing-test-first rule.** It is stated in
  `CONTRIBUTING.md` and that is all it is; a squashed commit passes every gate.
- **No mechanism stops documentation going stale.** Every correction in Phase 07
  was found by reading code against prose by hand — which is exactly how a false
  `rename()` claim survived two phases in `docs/TECHNICAL.md`. There is no doc
  test, no `--help` snapshot and no link check in CI. The verifier's labels are
  now pinned by a test; nothing else in the documentation is.
- **The research reports are dated snapshots, not claims about this commit.**
  Re-running any of them is hours of compute. `coverage-report.md` is already
  known stale in one cell (see above).
- **The migration recipe in the upgrade guide has never been run against a
  library 0.1.0 actually organised.** It follows from how the code reads
  metadata and from what a move does to a modification time; it is not a tested
  procedure, which is why every step of it is a preview first.
- **Only a bug report issue template.** No feature request template and no
  `config.yml`, so GitHub still offers a blank issue and nothing routes a
  security report away from the public tracker before it is opened.

## Two corrections this report produced

Writing it meant reading the changelog's `### Known issues` block against what
the code does today, and two entries did not survive that.

- **The sub-two-byte panic was not listed at all.** A crash a user can reach in
  the *default* posture, absent from the one document that user reads. Added,
  with the exact assertion, the exit code, and the two-byte boundary.
- **"`duplicates/NNN` group numbering is not stable across runs" had become
  false.** Phase 06 made duplicate grouping deterministic — `hasher.rs:552`

  and `test_find_duplicates_is_byte_identical_across_repeated_runs` pinning it —
  and the phase note said so at the time, but the changelog entry was never
  retired. Removed. A changelog carrying a stale limitation is worse than one

## What v0.2.1 should carry

In the order they cost a user something, not in the order they were found:

1. **The sub-two-byte panic.** A preview must never take the process down.
2. **The verifier's stale manifest**, and a zero-confirmed run exiting non-zero.
   A safety feature that silently confirms nothing is worse than its absence.

   most exposed to is the one CI never exercises.
