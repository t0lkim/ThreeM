# v0.3.2 Readiness

The honest status of ThreeM at `d977ebd`, the commit tagged `v0.3.2`. Every
figure below has a command behind it. Where something was not measured, this
says so rather than rounding it up to a claim.

It is written at a different moment from [[v0.2.0-readiness]]. That report was
written *before* a tag, to decide whether to push one. This one is written after
the tag and **before publication**: v0.3.2 exists as a **draft release**, and
whether it becomes public is a decision nobody has taken yet. That is by design —
the `--draft` change exists so the point of no return is somebody reading the
release page rather than a tag landing.

**Verdict: the draft is fit to publish.** No defect a user can reach was found
at this commit, which is not the same statement as there being none. All three
live defects the v0.2.0 report opened with are closed, and each was re-checked
against today's source rather than carried forward from a changelog entry. What
this release carries instead of live defects is a list of gaps in its own
*verification*, and one finding that is a defect in the release machinery rather
than in the tool — [the release gate is not the gate it says it
is](#the-release-gate-is-not-the-gate-it-says-it-is).

Publishing is one command — `gh release edit v0.3.2 --draft=false` — and it is a
human's to run.

One consequence of the draft state worth knowing before anybody links to it: a
draft's asset download URLs are namespaced under an `untagged-…` path rather
than `/download/v0.3.2/`, so **the current URLs are not the ones the release will
have**. Nothing in the repository links to them, which is why this is a note
rather than a defect.

## The release gate is not the gate it says it is

The `gate` job in `.github/workflows/release.yml` carries a comment describing
itself as "the same gate `ci.yml` runs on every push, run again here against the
tagged commit". It is not, in two respects, and both were found by reading the
two files against each other rather than by watching either go green:

- **It does not pass `--locked`.** `ci.yml` passes it on every cargo invocation
  that resolves dependencies — clippy, test, build, `llvm-cov` — and
  `release.yml`'s own `build` job passes it too (`release.yml:197`). Only the
  gate's `clippy` and `test` steps omit it (`release.yml:153`, `:157`). A stale
  `Cargo.lock` is therefore silently updated in-runner on the one job that runs
  against a tag. Closing `--locked` in CI was named as an open item by the
  v0.2.0 report and *was* closed there; this is the copy that was missed.
- **It has no timezone matrix.** `ci.yml`'s `test` job runs three zones — `UTC`,
  `Asia/Singapore`, `America/New_York` — because the machine's zone is an input
  to this crate. The release gate runs whatever the runner's zone is, which is
  UTC. This matters concretely rather than theoretically: **the defect this
  phase found in `EXPECTED.md` was red for eight hours a day east of Greenwich
  and green in UTC**, so a tag pushed during that window would have passed this
  gate on a tree the push gate would have failed.

**Neither is being changed here, and the reason is not that they are small.**
The previous task verified the release automation end to end by executing this
exact file twice and reading what it did; editing it inside a report-writing
task would invalidate that evidence and leave the workflow that ships v0.3.2
different from the one that was rehearsed. It is instead the first item of
[What v0.3.3 should carry](#what-v033-should-carry) — which is this project's
only mechanism for scheduling anything, a limit discussed under [Recording
versus scheduling](#recording-versus-scheduling).

Separately and more mildly: the `fuzz` job's `cargo fuzz run` also passes no
`--locked`, and `code/fuzz/Cargo.lock` is the file that went stale across two
releases before anybody noticed.

## The gate, as measured at this commit

```console
$ cd code
$ cargo fmt --check                                    # exit 0
$ cargo clippy --locked --all-targets -- -D warnings   # exit 0
$ cargo test --locked --all-targets                    # 674 passed, 0 failed, 0 ignored
$ cargo build --locked --release                       # exit 0
```

**674 tests**, from 630 at the v0.2.0 tag and 25 at the start of the playbook.
The scenario suite is ~28 s of the run and is now the slowest single target,
because it drives the `mmm-fixtures` binary end to end twice.

CI runs **fourteen legs** on `push` and `pull_request`: `test` over two
platforms × three timezones, and `msrv`, `coverage`, `fuzz` and `release-build`
over both platforms. MSRV is **1.87.0**, read out of `code/Cargo.toml` by the
job rather than written into the workflow.

**The MSRV rationale changed in this release even though the number did not.**
Both `CONTRIBUTING.md` and `Cargo.toml` said the library and binaries built on
1.86 and only the test fixtures needed 1.87. That stopped being true when the
fixtures moved into `src/fixtures.rs` and took a 1.87-only `u64::is_multiple_of`
call into shipped library code. Nothing a user runs changes; the explanation
somebody reads before trying to lower the floor was wrong in two files.
**Derived from the call site, not re-measured against a 1.86 toolchain** — that
would have meant installing one to confirm a documented stabilisation.

**The rise is not the generator flattering the total.** Excluding `fixtures.rs`

Both figures moved by fractions and **both were chased rather than waved
through**: `organiser.rs` gained ~490 net lines with two new uncovered clusters,

reopened); `journal.rs` has **no uncovered non-test lines at all**, so its −0.17

**`fixtures.rs` and `generate.rs` get no floor, stated plainly.** They fail the
test the floors were built around — they write disposable files into a directory
the user nominated, so the worst outcome is a bad demo library rather than a lost
photograph. Their coverage is *incidental*: nothing asserts their own branches,
so a floor would fire when somebody deleted an unrelated organise test. The
stronger gate is `tests/generated_library.rs`, which is what actually caught a
defect in that code.

**Three qualifications.**

- **Still no branch data.** `cargo llvm-cov` reports none for this crate, so a
  line counted as covered may have taken only one of its two outcomes. This is
  the entire reason the mutation pass exists. Region coverage is reported
  alongside as the closer proxy.
- **`hasher.rs` lost 1.03 points on byte-identical source**, and `sidecar.rs`
  gained 0.36 the same way — what the surrounding suite incidentally executes
  moved. **Nobody has explained it.** Attributing it needs a coverage run at the
  old commit, which was outside the task. Recorded as an open thread rather than
  smoothed over.
- **The Δ column is looser than it looks.** The v0.2.0 figures were measured at
  603 tests, before the mutation task added six more, and were never re-measured.
  Every Δ spans the fixtures move, those tests and two releases of feature work
  at once. Direction, not attribution.

The report's own figures are one macOS snapshot; the *floors* are enforced on
both platforms, which is stronger than the snapshot behind them.

## Mutation testing

`cargo-mutants` 27.1.0, six modules, **440 mutants, two hours at `-j 4`**. Full
detail in [[mutation-testing]].

| | Baseline | After |
|---|---:|---:|
| Caught | 351 | **356** |
| **Missed** | **27** | **22** |
| Unviable | 61 | 61 |
| Timeout | 1 | 1 |
| **Score** (caught ÷ viable) | 92.61% | **93.93%** |

Two modules the v0.2.0 report named as never mutated — `undo.rs` and
`sidecar.rs` — were measured this time rather than restated as a gap. **`undo.rs`
is the least-verified module in the crate at 79.71%**, against 88–100% for
everything else.

**All eight survivors the v0.2.0 run accepted are the same survivor, at the same
site, with the same reason** — checked one at a time against the source and
tabulated, not inferred from the count matching. The timeout is the same
timeout. **Four new survivors appeared** in those four modules across two
releases, which is the answer to why re-running beats re-reading.

**The two that mattered were in the collision ledger.**
`DestinationLedger::seed_from_disk` could be replaced with `()`, or have its `!`
deleted, and all 665 tests passed — that function is what makes the preview
account for names already on disk. It survived because **every existing preview
test organises into an empty directory**, including the one written for the
0.3.0 fix that added the ledger.

**Every claimed kill was verified in the failing direction:** five injections,
five catches by the intended assertion, each source restored and `diff`ed
byte-identical.

**What it does not cover.**

- **Eight survivors remain in `undo.rs`'s restore counters**, so `mmm undo`'s
  `failed` and `restored` figures are unasserted on every error path — the
  numbers a user reads to decide whether their library came back. Closing it
  needs the organiser's failure-injection seams extended to the restore loop.
- **The "after" column is a substitution, not a second sweep.** Five mutants
  re-run scoped by regex; 427 outcomes carried across. Same shortcut the v0.2.0
  report took, stated for the same reason.
- **Nine modules have still never been mutated:** `naming.rs`, `config.rs`,
  `settings.rs`, `settings_report.rs`, `scanner.rs`, `xmp.rs`, `reporter.rs`,
  `timezone.rs`, `geocoder.rs`.
- **Still no CI gate.** Two hours a run is too slow for a pull request and
  `--in-diff` remains unevaluated. Nothing stopped four new survivors appearing
  between the two runs, and nothing stops the next four.
- **The v0.2.0 comparison is direction, not arithmetic.** Its 96.98% was itself
  a substituted figure, and the four modules gained 30 mutants across two
  releases.

## Fuzzing

**Five** `cargo-fuzz` targets under AddressSanitizer, **15.9 million executions
in fifteen minutes, no crash, no hang, no allocation failure.** Toolchain
`nightly-2026-05-01` (rustc 1.97.0-nightly). Full detail in [[fuzzing]].

| Target | Executions | Crashes |
|---|---:|---:|
| `parse_iso6709` | 5,535,414 | 0 |
| `parse_wall_clock` | 4,785,525 | 0 |
| `parse_offset` (new) | 4,381,968 | 0 |
| `journal_line` | 4,065,603 | 0 |
| `xmp_sidecar` | 1,490,229 | 0 |

**There were four targets and there should have been five, and finding that out
is the whole return on re-running rather than re-reading.**
`timezone::parse_offset` reads an EXIF `OffsetTimeOriginal` tag — bytes written
by camera firmware, the exact definition the other four were selected by — and
it had no target and was not named as a gap. It landed one day before the report
that overlooked it: the parser was newer than the survey, and nobody re-ran the
survey.

It earns a target on its own terms. `chrono` publishes no offset parser, so
`parse_offset` splices the tag into a whole datetime string and parses *that* —
a wider surface than the three spellings it documents — and the value decides
**which calendar day a photograph is filed under**. The failure mode is a
misfiled photograph rather than a crash, so the target asserts the ±24h domain
and a round trip through `Display` rather than only the absence of a panic.
**Verified in the failing direction:** with the parser altered to return the
offset plus one second it failed in under a second.

**The pin holds, checked 2026-08-10.** Nightly 1.99.0 fails identically at
`nom-exif-1.5.2/src/exif/io.rs:65`, and 1.5.2 remains the last of the 1.x line.
The date is now recorded beside the error in `code/fuzz/README.md`, so the next
check is a comparison rather than a re-derivation.

**`--target "$host"` is still at `ci.yml:316`**, as are both action pins.
Confirmed by reading, which is the only way — a green CI run does not
distinguish these being present from their absence until the day an installation
detail changes.

**Gaps.** Nothing runs long (three minutes here, sixty seconds in CI). Three
parsers are still unfuzzed — the TOML settings loader, `undo.rs`, and the
scanner's path handling. The corpus is hand-written seeds; there is no
structure-aware fuzzing; `xmp_sidecar` is still explored at libFuzzer's 4 KB
default and is the slowest target by a factor of three. And **nothing stops the
next parser landing without a target** — no test asserts that `src/fuzz.rs`
covers the parsers `metadata` and `xmp` actually call, which is exactly how the
offset tag went a day unfuzzed and a report unmentioned. That is a gap in the
*process*, and it is the one most likely to repeat.

## The generated library, and what it is for

The largest user-visible change in 0.3.2 is `mmm-fixtures`, and its claim is
unusual enough to be worth stating: the sensible reaction to a tool that moves
photographs is to refuse to point it at your own, which leaves a new user with
nowhere to start. The generator writes a throwaway library of byte-valid images
and videos carrying real EXIF, and ships **`EXPECTED.md` beside it naming every
file and where it should end up**.

That document is the whole point, and it is also the thing most able to be
quietly wrong, so it is verified three ways:

- `tests/generated_library.rs` generates, organises and asserts every file
  reached its predicted directory — identified by the provenance marker in its
  bytes rather than by filename, which is what the organiser rewrites.
- `tests/scenario.rs` does the same thing **through the binaries**: it runs
  `mmm-fixtures` as a binary, reads `EXPECTED.md` back off disk, **parses it as
  prose**, and holds every row of every table against the organised tree. A
  claim that survives in the `Plan` and is lost on the way into the document
  passes the first test and fails this one. The parser **panics on a heading it
  does not recognise**, so a renamed section fails loudly rather than being
  skipped.
- `the_printed_seed_rebuilds_the_library_it_was_printed_for` runs the binary
  **unseeded**, reads the seed it printed and rebuilds from that — so what is
  tested is the seed a bug reporter would paste, not a constant the test chose.

**This machinery found a real defect in itself, which is the argument for it.**
`EXPECTED.md` was being written in two timezones at once: dated fixtures
predicted at the wall clock as written, filesystem-dated fallbacks predicted by
reading the mtime in `DateTime<Local>`. The two frames agree only on a machine
already running UTC, which is why CI's UTC leg never saw it. Two consequences,
the second worse than the flake — the suite was red for eight hours a day east
of Greenwich, and **the document told the reader to organise with no `--timezone`
at all**, so any reader outside UTC got a correct run and a document declaring
every dated file misfiled, against a section reading "if one of them lands
anywhere else, that is a defect". Fixed by putting the whole document in one
frame, and guarded by a unit test whose instants fall on a different calendar day
under *both* non-UTC legs of the CI matrix, so a revert fails there rather than
nowhere.

**A library generated before 0.3.2 carries the old document.** Regenerating with
the same `--seed` produces a corrected one; the library bytes are unchanged.

Not covered: the `stress` and `minimal` profiles are not driven through the
binary-level test (600 files, and a subset of shapes already covered), and the
preview is not compared against the committing run for a generated library.

## Release automation and packaging

The v0.2.0 report's headline packaging limitation was that the release workflow
had never run, so the first real tag would also be its first execution. That is
closed, and closed in the order it should have been:

| Rehearsal | Run | Result |
|---|---|---|
| `workflow_dispatch` at `version=0.3.1` | [31359501233](https://github.com/t0lkim/ThreeM/actions/runs/31359501233) | 3m40s, all six jobs green, `publish` skipped with zero steps |
| `workflow_dispatch` at `version=0.3.2`, after the bump | [31360234875](https://github.com/t0lkim/ThreeM/actions/runs/31360234875) | 3m50s, green. Exercised the two checks the first could not: the version match against the bumped manifest, and `changelog-section.sh 0.3.2` |
| The tag itself | [31360515539](https://github.com/t0lkim/ThreeM/actions/runs/31360515539) | All jobs green, `publish` included, `--draft` did what it was added to do |

**Two of the three published binaries had never been started.** The workflow's
architecture check and smoke run each named `mmm` and nothing else, so
`mmm-dedup-verifier` and `mmm-fixtures` were built, checksummed, attached to a
release and put on people's `PATH` with nothing having established they could
run — least of all on `x86_64-apple-darwin`, which is cross-built on an arm64
runner. **The packaging metadata itself was always correct**; what was missing
was any evidence the files worked. Both steps now iterate a binary list read out
of `package-release.sh` at run time, so the set checked is by construction the
set that ships, and `tests/release.rs` already held that line against the crate's
`[[bin]]` targets — so the chain closes.

**`--version` is a low bar and the smoke run no longer stops there.** clap
answers it before `main` runs. Each binary now does real work: `mmm` a dry run,
`mmm-fixtures` a `minimal` library that must produce a non-empty `EXPECTED.md`,
`mmm-dedup-verifier` a refusal of a path that is not a directory.

**Rosetta executed rather than skipping**, which closes an item recorded as open
one task earlier. No `::notice::` was emitted anywhere in the run — grepped for,
since the skip is silent by design — and the timing corroborates it: the
`x86_64-apple-darwin` job's first `mmm --version` took **2.57 s against the arm64
job's 0.048 s**.

**The assets were checked rather than read off the release page.** Both macOS
archives were downloaded from the release itself, `shasum -a 256 -c` verified,
unpacked, and all three binaries run out of the archive — right architecture, all
reporting `0.3.2`, `mmm-fixtures` writing a 91-line `EXPECTED.md`, `mmm`
previewing that library and creating nothing.

**Still not exercised.** `publish` has never run on a dispatch and cannot — its
artifact chain was reproduced locally, which is an argument that it would work
rather than evidence that it did. **The Linux tarball's binaries have never been
run from the tarball**; they ran on the runner from the build tree. No Linux
machine to hand.

## One correction this report produced

**`docs/research/coverage-report.md` says the verifier defect is open, and it is
not.** Under `bin/mmm_dedup_verifier.rs`, the report qualifies its coverage
figure by noting that "the v0.2.0 readiness report records that
`mmm-dedup-verifier` confirms nothing and exits 0 against a stale manifest" and
that "nothing in this measurement bears on that". The first half is true of the
v0.2.0 report; the implication that the defect is still live is false. **It was
fixed in 0.3.0** — two releases before the coverage report was written, on
2026-08-10.

The qualification's *point* still stands and is worth keeping in some form: a
suite can execute every line of a tool that reaches the wrong verdict, so 96.70%
line coverage is not an argument that the verifier is correct. What was wrong was
the example it reached for. The paragraph has been corrected in place rather than
deleted, because the reasoning is the part worth having.

This is the same failure mode the v0.2.0 report named in its own process
section and the same one the documentation task found twice in this phase: **a
claim that explains rather than repeats is not machine-checkable, and the only
thing that catches it is a person reading prose against code.** Two of the three
were found that way; this one was found by reading three documents against each
other while writing a fourth.

## Known limitations

Everything below is true of `d977ebd`, grouped by what it costs a user.

### Safety and correctness

- **`TimezoneSource::GpsDerived` is declared and nothing produces it.**
  Coordinates → zone needs a boundary database. Unchanged since v0.2.0.
- **`unsorted/` is unreachable through the CLI except via `--require-exif`.**
  Every file has a filesystem timestamp, so an undateable photograph is filed
  under the date it was *written*. 0.3.0 fixed the *summary* that miscounted
  this; the behaviour is unchanged and remains an open product question.
- **`.mmm/journal` is the only record.** Delete the output tree's `.mmm/` and the
  run is unreversible; nothing warns before that happens.
- **`mmm undo`'s error-path counters are unasserted** — see the eight surviving
  mutants above. The tool reports numbers during a recovery that no test checks.
- **Three format cells remain unverified for want of a fixture**: `.cr3` date and
  GPS, the Android `moov/udta/©xyz` MP4 GPS path, and GPS in a `.3gp`. Eleven
  further ❌ rows are derived rather than measured. Unchanged since v0.2.0.
- **No TIFF-based RAW is dated from the RAW itself**; an `.xmp` beside it is the
  only route. Unchanged.
- **An Apple `creationdate` of exactly `+00:00` is read as an instant**, so a
  video shot in the UTC zone can still lose its wall clock. Unchanged.

### Platform

**Four of the v0.2.0 platform limitations are closed, and were verified closed
by reading `ci.yml` rather than assumed from a changelog:**

- A timezone leg exists — `test` runs `UTC`, `Asia/Singapore` and
  `America/New_York`, and this is the matrix that made the `EXPECTED.md` defect
  catchable.
- `msrv`, `coverage` and `fuzz` all run on both platforms now, not Linux only.
- `--locked` is passed on every dependency-resolving cargo invocation in
  `ci.yml`.
- The fuzz gate runs under both sanitiser runtimes rather than one.

What remains:

- **Windows has never been compiled, let alone run.** No Windows leg in any
  matrix and no Windows target in `release.yml`. `organiser::errno` is
  `cfg`-split for Linux and macOS only, and the `#[cfg(unix)]` tests — a dozen of
  them, including every permission-dependent one — simply do not exist there.
- **The release gate is weaker than the push gate**, in the two respects
  [above](#the-release-gate-is-not-the-gate-it-says-it-is).
- **`cargo fuzz run` passes no `--locked`**, and `code/fuzz/Cargo.lock` is
  precisely the file that has gone stale before.

### Release and packaging

- **Nothing is signed or notarised.** macOS quarantines every one of these
  downloads until the attribute is cleared. The README and User Guide now say so
  — that is new in 0.3.2 — but the artifacts are unchanged. Checksums prove the
  file arrived intact, not who built it.
- **glibc, not musl.** The Linux archive will not run on an older distribution.
  No static target and no Windows target at all.
- **The Linux tarball's binaries have never been executed from the tarball.**
- **`publish` has never run on a `workflow_dispatch`** and cannot; only real tags
  exercise `gh release create`.
- **`keywords` and `categories` are still unvalidated.** `cargo publish
  --dry-run` was not run, because the crate is not published and that path talks
  to the registry.
- **`forgejo/main`'s state is unknown, not known-behind.** `forgejo.daisynet.io`
  does not resolve from this machine, so the mirror could not be checked let
  alone pushed. The v0.2.0 report's "66 commits behind" figure is **not** carried
  forward, because carrying a stale number forward as though it had been
  re-measured is the thing this report exists not to do.

### Process

- **Nothing enforces the failing-test-first rule.** It is stated in
  `CONTRIBUTING.md` and that is all it is.
- **Nothing stops the next parser landing without a fuzz target**, as above.
- **No mutation gate in CI**, so nothing stops the next surviving mutant.
- **The research reports are dated snapshots, not claims about this commit** —
  and one of them was wrong in a way this report had to correct.
- **Documentation drift is now partly machine-checked and mostly not.**
  `tests/docs.rs` asserts every `[[bin]]` the crate declares is named in the
  README, the User Guide and `CONTRIBUTING.md`, and that the `--profile awkward`

## Recording versus scheduling

The v0.2.0 report named a process failure and asked that this one be honest
about whether it repeats: **a defect recorded in a playbook note is not a defect
anybody is going to fix.** The sub-two-byte panic reached a release having been
written into five consecutive task notes.

The honest answer for this phase is **mixed, and the mechanism that worked is
identifiable.**

**It worked once, and the shape is worth copying.** The coverage task found that
nothing ran `mmm-fixtures --profile awkward`, so the trailer telling a user the
malformed files are deliberate was never executed. It **named the documentation
task as the owner** rather than filing the observation. The scenario task then
executed it and said explicitly that executing is not asserting, keeping the
hand-off alive. The documentation task asserted it, in both directions. Three
tasks, one named owner, closed. The same mechanism carried the version-match
rehearsal from the automation task into the release task as a *step*.

**It did not work everywhere, and this is where each thing actually stands:**

- The eight `undo.rs` counter survivors are named in [[mutation-testing]] **and**
  in the changelog. That is better than a playbook note, because both are files a
  user or contributor reads. It is not a schedule — nothing fails, nothing is
  assigned, and there is no issue tracker to file it in.
- `hasher.rs`'s coverage movement, the unfuzzed process gap, the unexecuted Linux
  tarball, and `forgejo/main` are all **recorded and not scheduled**. Saying so
  is the most this report can do about them.
- **The release gate finding in this report is the live case.** It was found
  today, it is not being fixed today, and the reason is given rather than
  implied. It is first on the list below. If v0.3.3 ships without it, this
  paragraph is the evidence that the mechanism failed again.

**The structural point.** Every "scheduled" item in this project is scheduled in
a document, because there is no issue tracker in use and no milestone. Documents
are read by people deciding what to do next, which is genuinely better than a
gitignored playbook note — the playbook is not even in the repository. It is
still not a mechanism that fails when the work is skipped, and only mechanisms
that fail are mechanisms.

## What v0.3.3 should carry

In the order they cost something, not the order they were found:

1. **Make the release gate the gate it claims to be** — `--locked` on its clippy
   and test steps, and the timezone matrix from `ci.yml`. It is the only gate a
   tag passes, and it is currently the weaker of the two. Found by this report
   and deliberately not fixed by it.
2. **The `undo.rs` restore counters.** Extend the organiser's failure-injection
   seams to the restore loop, so the numbers a user reads mid-recovery are
   asserted. `undo.rs` is the least-verified module in the crate.
3. **A test that fails when a parser of third-party bytes has no fuzz target.**
   This is the gap that already cost a target for a day and a report for a
   revision, and it is the one most likely to repeat.
4. **A real verification run for `mmm-dedup-verifier`** somewhere in the suite —
   it is a read-only tool whose entire purpose is to be believed before somebody
   deletes files, and only its refusal path is exercised in the release job.
5. **Explain the `hasher.rs` coverage movement**, or stop reporting Δ columns
   that nobody can attribute.
6. **Publish the draft, or decide not to.** Until then v0.3.1 is what a user
   gets, and the three binaries verified above are attached to nothing anybody
   can reach.
