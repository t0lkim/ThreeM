# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **BREAKING — the date tree is now one directory per day, `YYYY-MM-DD/`, not the three-level `YYYY/MM/DD/` hierarchy.** `2024/03/15/` becomes `2024-03-15/`. A single component globs (`2024-03-*`), `cd`s and copies as one path rather than three. **An existing library organised under the old layout is not migrated**: a run against it creates flat directories alongside the old tree, so the same day can end up in both places. Reorganise deliberately — `mmm undo` the old run if a journal exists for it, or move the files yourself — rather than assuming a later run will merge them. The *filename* is unchanged; it was already `YYYY-MM-DD-HHMMSS[-location].ext`.
- **BREAKING — previewing is now the default; moving files requires `--commit`.** A bare `mmm ~/Photos` scans, plans, prints the planned moves and exits without touching a single file. Passing `--commit` is the only way to move anything. Output defaults to the first input directory, so the most natural invocation used to rewrite the user's photo library in place with no confirmation and no undo. See [`docs/decisions/adr-001-dry-run-by-default.md`](docs/decisions/adr-001-dry-run-by-default.md).
- Deduplication is gated by `--commit` as well — a preview run reports the duplicate groups it found without creating a `duplicates/` directory.
- A posture banner is printed **before the scan**: `DRY RUN — no files will be modified. Re-run with --commit to apply.` or `COMMIT MODE — files will be moved.`
- `--help` states the safety posture in three places: a `SAFE BY DEFAULT` summary, the `--commit` flag's own text, and a `SAFETY` + `EXAMPLES` block.
- **`--no-prompt` accepts an explicit value: `--no-prompt=false` keeps the chunk prompts.** `--no-prompt` on its own still means yes. The value has to be attached with `=`, so `mmm --no-prompt ~/Photos` still reads the path as a directory. Without this there would be no way to answer a `no_prompt = true` written into a config file, and a switch that can only be turned on is not a precedence rule.
- `--chunk-size` no longer carries a built-in clap default (`--help` still names 100 as the default). A default at the flag would arrive as an opinion of the *command line* — the highest-priority layer — and would have silently outranked every `chunk_size` any config file could set.
- **BREAKING (library) — `Config::output_dir` and `Config::resolve_journal_dir` take `&Settings`, and `JournalLocation::resolve` does too.** `Config` is now purely what the command line said; `Settings` is the resolved runtime type the pipeline reads. `Config::chunk_size` and `Config::no_prompt` are `Option<usize>` / `Option<bool>` so "not passed" stays distinguishable from "passed the default". New: `Cli::settings_layer`, `Config::settings_layer`, `JournalLocation::settings_layer`, `JournalAction::location`, and `reporter::CHUNK_PROMPT_PREFIX`.
- Tracing is initialised *after* the config layers are read, so a `verbose` set in a file reaches the subscriber. A config error is therefore reported through the process's exit rather than through the log — which is where an error naming a file and a line belongs anyway.
- **Which copy of a duplicate group is kept is now a rule, not a coin toss: the shallowest path, then the lexicographically smallest.** Of `photo.jpg` and `backup/old-phone/photo.jpg`, the top-level one stays where it is and the nested one goes to `duplicates/NNN/`; between `a.jpg` and `b.jpg` in one directory, `a.jpg` stays. The cascade's working sets are `HashMap`s and a `HashMap` iterates in a randomly seeded order, so **which of somebody's photographs was left alone and which was moved aside was previously decided by that seed** — two runs over the same untouched library could disagree, and macOS and Linux reliably did. Two consequences beyond the retained copy: `duplicates/NNN` numbering now follows the groups' BLAKE3 digests rather than a random order, so a group keeps its number between runs over the same tree; and the order files are planned in is settled by the same rule, so which of two files competing for one name gets `photo.jpg` and which gets `photo-1.jpg` no longer varies run to run. **On upgrade:** a re-run over a library the old code already deduplicated may keep a different copy than that run did, because the old choice was arbitrary — there is no prior behaviour being broken, only an arbitrary one being replaced. Nothing is renamed or re-filed by this alone; it only decides which member of a group moves.
- **Deduplication hashes on every available CPU core instead of one.** The two hashing phases now run as parallel iterators over their whole candidate set rather than one size group at a time — which matters more than the threading does, since duplicate groups are usually pairs and hashing *within* a group would have capped the work at two cores. Measured on an 8-core M1 Pro over the project's benchmark corpus: the full-hash phase, which is 92% of the cascade, fell from 94.35 ms to 42.42 ms (2.22×), and the partial-hash phase from 3.65 ms to 1.57 ms (2.33×). Phase 1 groups by size and reads no file content, so it stays serial. Nothing about the *answer* changes: the retained copy, the group order and the plan order are all settled by sorting after the hashing finishes, so thread completion order cannot reach the output, and a file that will not read is still excluded with a warning and counted — exactly once — rather than taking the run down. **Limits of the measurement:** the benchmark re-reads the same corpus, so it is page-cache-warm and measures BLAKE3 plus syscalls, not cold disk; a first run over a library that is not in cache will gain less, and on a spinning disk or a network share the concurrent seeks may cost more than the parallel hashing saves — which is what `--threads` (below) exists to answer. (This briefly left the progress bar advancing once per phase; it now advances once per file — see the progress-bar entry below.)
- **A file of 64 KB or less is no longer read twice by the duplicate scan.** The partial-hash phase reads the first 64 KB of a candidate to fingerprint it — which, for a file that size or smaller, is the whole file. That digest is therefore already the file's content hash, so the full-hash phase now takes it as given instead of opening the file again to recompute it. A library of screenshots, thumbnails, icons and sidecar-sized files halves the bytes the scan reads. Measured over a 250 MB tree of 6 400 duplicate 40 KB files on an 8-core M1 Pro, page-cache warm: a preview run's total wall clock fell from 0.61 s to 0.52 s (median of seven), and the full-hash phase went from 6 400 reads to none. **Limits:** the boundary is 64 KB and not a byte more. Between 64 KB and 128 KB the partial hash covers only the first 64 KB — a tail read there would overlap the head — so files in that band are still fingerprinted on their opening bytes and still read a second time to confirm. Anything above 128 KB, which is most photographs, is unaffected: the saving here is real for small files and zero for large ones. The duplicate groups themselves are identical either way; this changes how they are established, not what they are.
- **Files small enough to be hashed whole by the partial-hash phase now record that hash in the journal.** `mmm undo` compares a file against its recorded digest before putting it back, and previously only files that reached the full-hash phase had one. The extra digests cost nothing — they were already computed — and they mean undo verifies content rather than length for that part of a run.
- **A file whose length has changed since the scan is now excluded from the duplicate scan and counted as skipped, instead of being hashed as it stands.** A file that is still growing or shrinking is usually one being written — a camera import, a sync client — and hashing whatever happens to be there files it under a length nothing else in the run agrees with: the size grouping used the old figure, the duplicate group reports it, and the journal records it as the evidence undo checks. It is reported like any other skipped file, with a warning naming both lengths, and the run continues. **Limits:** this closes the window between the scan and the hash, not the one after it. Nothing can promise a file did not change after its last byte was read.
- **The duplicate-scan progress bar advances once per file and finishes full.** It used to be told the scan count and then ticked once per phase — so it stood still through the phase that takes 92% of the run and, on any library where most files have a size nothing else shares, stopped at something like `40/12000` and simply exited. Both halves of that are fixed, and they are the same fix: the bar now counts **reads**, and it counts them as each one lands.
  - **It reaches its total by doing the work**, not by being told at the end that it is finished. `0/0` on a library with no size collisions at all is the honest answer there — nothing was opened.
  - **Counting files rather than reads would have made it lie about where the time goes.** Grouping by size retires most of a library in microseconds without opening anything, so a bar that ticked per file would leap to 90% in the first millisecond and then spend the entire run on the last tenth. It therefore starts counting at the first phase that reads file content, and its message says which phase that is.
  - **It never goes backwards.** Each file entering the partial-hash phase is charged for two reads — the partial hash, and the full hash it may go on to need — and the second is refunded for every file the partial hash rules out. The obvious alternative, charging the full read only once it is confirmed, is the same arithmetic run the other way: the bar would reach 100% at the end of the partial-hash phase and then fall back for the phase that takes 92% of the time.
  - The phase message and the counter cannot disagree: each phase collects before the next begins, so `Phase 3` is never displayed beside reads the previous phase still owes.
- **BREAKING (library) — `hasher::group_by_partial_hash` and `hasher::group_by_full_hash` take a `&ProgressBar`** (second of three arguments), ticked once per file as its read completes. Pass `ProgressBar::hidden()` where there is nobody watching. `find_duplicates` is unchanged in signature but now owns its bar's position, length and message for the duration of the call.
- `find_duplicates` takes `&[ScannedFile]` instead of consuming a `Vec`.
- **BREAKING (library) — `scan_directories` and both `group_by_*` functions no longer return `Result`.** They return `ScanResult { files, skipped }` and `HashGroups { groups, skipped }`. There is no error channel left to abort a whole run through, which is the point: "one bad file took the library down" is now unreachable rather than merely fixed.
- **BREAKING (library) — `execute_move` returns `MoveOutcome`, not `()`.** A file planned for `photo.jpg` can land at `photo-1.jpg`, and a record that cannot name the file's actual path cannot be used to put it back.
- **`hasher::partial_hash` is private, and takes the scan-time size again — this time as a check rather than as a buffer length.** It sized a `read_exact` from the scan figure once and failed the whole run when a file had shrunk; it then stopped taking the figure at all and hashed whatever was there. It now takes it back and *compares*: the length is read from the open handle, and a file that no longer matches what the scan recorded is refused as a per-file skip (see the entry above). The digest is still computed only from bytes actually read.
- `reporter::print_summary` takes a `RunSummary` struct instead of five positional `usize` arguments — seven same-typed figures transpose silently, and two of them exist specifically so omissions cannot go unnoticed.
- `Files scanned:` is the scan count rather than `unique + duplicates`. Those were equal before, and stop being equal the moment a file is skipped.
- `README.md`, `docs/USER-GUIDE.md` and `docs/TECHNICAL.md` updated so no example command that moves files is missing `--commit`.
- `docs/USER-GUIDE.md` corrected where it stated safety guarantees that were no longer true — it promised moves "use `rename()`" and that a cross-volume copy is verified by size, both of which this phase replaced, and its "you can stop at any chunk" note now says the run finishes properly and prints the same summary a completed run does.
- `docs/TECHNICAL.md` gains **Resilience**, **Stopping a run part-way** and **Path Derivation** sections, and its Manifest File Format section states the write ordering as the safety property it is.
- `docs/USER-GUIDE.md` gains an **Undoing a run** section covering `mmm undo`, `mmm journal list` / `show`, the per-file outcome table, the interrupted-run report and the exit-code contract; `README.md` lists `mmm undo` among the features. `docs/decisions/adr-003-atomic-move-semantics.md` no longer describes reversing a run as an open gap.
- **`docs/TECHNICAL.md`'s dedup cascade section rewritten for the parallel cascade, and one thing it said was wrong.** It described the partial hash as "128KB read per file (first 64KB + last 64KB)" with a footnote that a file under 128KB reads only the first chunk — which reads as an edge case and is in fact a rule with three bands, one of which surprises people: between 64KB and 128KB a file is fingerprinted on its opening bytes and nothing else. That is now a table, beside which phase is parallel and which is serial, the `(size, digest)` bucket key phase 2 needs, the promotion that lets phase 2 settle a small group without a second read, the ordering rules that make the output the same on every run, and how the progress bar's read accounting works. New **Determinism**, **Concurrency** and **Progress accounting** subsections; the cascade diagram shows the promotion path; `rayon` and `criterion` are in the dependency table; the build commands list `cargo bench`.
- `docs/USER-GUIDE.md`'s **How many threads** section links the decision record for why the scan is parallel and why the default is capped at 8.

### Deprecated

- `--dry-run` / `-d` is now a hidden no-op, kept so existing scripts do not fail on an unknown argument. Passing it prints a one-line deprecation notice to stderr. `--dry-run --commit` resolves to commit — the retired flag is a no-op, not a veto.

### Added

- **The whole journey is now tested once, over a library rather than a handful of files.** [`code/tests/scenario.rs`](code/tests/scenario.rs) builds 358 synthetic files across nested directories — twelve rolls of EXIF-dated JPEGs, HEIC stills, TIFF RAW dated by the XMP beside it, MP4 and MOV clips, GPS-tagged photographs, ten duplicate pairs and a trio, sidecars in both naming conventions, six files with no date of their own, orphaned sidecars, non-media files and empty directories — then previews, commits, checks the output against a golden tree, and undoes the lot. Three claims are asserted that only mean anything at this scale: **conservation** (the multiset of content hashes across input-plus-output is the same before and after, so nothing is lost, duplicated or invented), **the plan is what happened** (every destination the dry run printed is a file the committing run produced, and nothing was organised that the preview did not list), and **reversibility** (after `mmm undo --commit` the input tree is byte-for-byte the tree that went in). The same journey is then run at `--threads 1` and compared with the parallel default, path for path and byte for byte.
  - **The suite was itself checked by breaking the code on purpose**, in the style of the mutation work below, because a large test that passes first time is as likely to be vacuous as correct. Four deliberate defects were injected and each was caught by the assertion meant for it: changing the default date-directory layout (golden tree), dropping one file per duplicate group (duplicate assertions), making the move clobber an existing destination instead of refusing it (conservation), and omitting a sidecar from the dry-run listing (the plan claim).
  - **Three things are deliberately not pinned,** because they are not predictable from the fixture and asserting them would make the suite flake rather than fail: which member of a duplicate group is relocated (scan order is the filesystem's, so every group is built from files sharing a leaf name and the *name* is pinned instead), the `duplicates/NNN` group number (content-hash order — asserted as a set of groups and a multiset of leaf names), and the date directory of a filesystem-dated file (the day the fixture was built — asserted as "a date directory that is none of the fixture's own", which holds at any hour including midnight).
  - **Cost and limits.** The two tests take about 22 seconds wall-clock, which is most of the integration suite's runtime. Duplicate *relocations* are excluded from the plan-versus-outcome comparison because they are reported by the duplicate listing rather than planned as moves; their journalling is proved in `undo.rs`. The run is driven with `--timezone UTC` so that a filesystem-dated file lands in the same directory in every zone — the default resolution order is exercised elsewhere, not here.
- **The four parsers that read bytes somebody else wrote are now fuzzed.** A camera's date strings, a video's location string, an XMP sidecar and a journal line all arrive from outside this tool, and a panic in any of them stops a run part-way through moving a library. `cargo-fuzz` targets for all four live in [`code/fuzz/`](code/fuzz/README.md), and a CI job runs each for sixty seconds on every push and pull request, starting from a checked-in corpus of hand-named seeds and past crashes. About 29.6 million executions under AddressSanitizer found **one defect** (below); results and reasoning are in [`docs/research/fuzzing.md`](docs/research/fuzzing.md).
  - **The predicted UTF-8 panic is not there, and it was measured rather than assumed.** `parse_iso6709` slices byte offsets into a `&str`, which looks like an index-out-of-bounds waiting for a multi-byte character. It is safe by construction: every offset it slices at is the position of a `+` or `-`, and an ASCII byte can never occur inside a multi-byte UTF-8 sequence. Seventeen million executions over multi-byte input agree. Written down so the next reader does not have to re-derive it.
  - **Limits.** The longest run was four minutes and the CI gate is one — enough to catch a returning regression or a shallow new panic, not a campaign. The XMP target was explored at libFuzzer's default 4 KB input ceiling, so a full-size Lightroom sidecar is outside what it saw. The TOML settings loader, `undo.rs` and the multi-line framing of `Journal::read` have no targets at all, and the corpus is three to six hand-written seeds per target rather than a few thousand real files. The toolchain is pinned to `nightly-2026-05-01` because the current nightly does not compile `nom-exif` 1.5.2 — a dependency problem, recorded with its exact error in `code/fuzz/README.md`.
- **The tests were themselves tested, by breaking the code on purpose.** Coverage says a line ran; it does not say anything looked at the result — and `cargo llvm-cov` reports no branch data for this crate, so a "covered" line may have taken only one of its two outcomes. `cargo-mutants` was run over `organiser.rs`, `journal.rs`, `hasher.rs` and `metadata.rs`, generating 313 deliberate defects. **Nineteen of them passed all 603 tests.** Eleven are now closed and six tests were added; the mutation score went from 92.83% to 96.98%. Full results, and the reason for every mutant left alive, in [`docs/research/mutation-testing.md`](docs/research/mutation-testing.md).
  - **Two of the eleven would have filed photographs under the wrong date.** Deleting the `EntryValue::Text` arm from either datetime reader broke no test: `nom-exif` hands most files over already parsed, so that arm fires only for the cameras that spell the tag their own way — the very people who would never have known their photographs were being filed under the date they copied them off the card. And the check that rejects the negative year `chrono` will parse out of a corrupt EXIF string could be replaced by a constant, letting every one of them through to produce a directory called `-44-03-15` at the top of a photo library.
  - **A file dropped by the second hashing read was never counted in a test.** That file is excluded from the plan — not moved, not reported as moved — and the count of them is all the operator has to know their library was only partly processed. The failure needs a file to survive one read and be gone by the next, which no test can arrange against a real filesystem, so the read is now injected in the same style as the existing cross-volume `copy` seam.
  - **`DateSource::is_filesystem` turns out to have no caller.** It is public API documented as the counterpart to `is_recorded`, and the tally it describes is computed by matching the variants directly elsewhere. It is now pinned by a test rather than deleted, and recorded in the report as the finding it is.
  - **Eight mutants are alive on purpose**, each with a reason in the report: a read-buffer length that cannot change any digest, a counter read only by a log line, two guards unreachable by construction (now commented at the site), a video-container date key that `nom-exif` 1.x never emits (measured with a probe, not assumed), two default trait-method bodies that the mutation leaves semantically identical, and one mutant that makes a loop run forever — detected by the suite hanging, which no assertion can improve on.
  - **Not covered:** only those four modules were mutated. `undo.rs` and `sidecar.rs` are destructive surfaces by this project's own standard and have not been mutated at all. There is no CI gate either — a run takes about an hour — so nothing currently stops a new surviving mutant from appearing.
- **The destructive paths are now measured, and CI fails if the measurement drops.** Test coverage is reported per module by `cargo-llvm-cov`, and `organiser.rs` and `journal.rs` — the code that moves files and the code that records the moves — carry a CI floor. Twenty-six tests were added on branches that only run once something has already gone wrong: a journal that dies *after* a photograph has moved (so the move is still counted and the run stops rather than accumulating more), a sidecar that cannot follow its parent, a duplicate group's manifest that stops being writable mid-group, every collision candidate taken, a copy that reports success without writing anything, a source that will not delete after a verified copy, and `undo` against a run id that was never recorded. Whole-crate line coverage went from 89.82% to 91.48%; `organiser.rs` from 86.20% to 92.76%. The full per-module table, and every uncovered line with a reason, is in [`docs/research/coverage-report.md`](docs/research/coverage-report.md).
  - **Two gaps are recorded rather than closed.** `bin/mmm-dedup-verifier` has no tests at all — it is read-only and cannot lose anything, but nothing proves it still parses the manifest format `organiser.rs` writes. And five branches in `main.rs` (the log after a failed journal close, and the two bails after a run or undo stopped by a journal failure) need an open file descriptor to fail mid-write, which is not reproducible portably; the equivalent stopping behaviour is proven at library level instead.
  - The figures are measured on macOS. The CI floors sit one point under them to absorb genuine platform differences, which is a margin for `#[cfg(unix)]` tests, not room for coverage to rot.
- **`--threads <N>` and the `hash_threads` config key bound how many files the duplicate scan hashes at once.** Without them the cascade hashed on every core it could find, which is right for an NVMe SSD and wrong for the storage a photo library is most often actually on: a spinning disk has one head, so every concurrent reader past the first turns a sequential read into a seek storm, and a network share pays a round trip per thread. **The default is now the machine's core count capped at 8** rather than uncapped — a 64-core workstation no longer fires 64 concurrent reads at somebody's library. On an 8-core machine or smaller nothing changes. `--threads 1` hashes one file at a time; the guidance per storage type is in [`docs/USER-GUIDE.md`](docs/USER-GUIDE.md#how-many-threads).
  - **The answer does not depend on the setting.** A run at `--threads 1` and a run at the default return byte-identical duplicate groups, the same retained original in each, the same `duplicates/NNN` numbering and the same plan order. Only the pace changes.
  - A count of `0` is **refused** rather than clamped, in a file, in the environment and on the command line, with the same message at all three: `rayon` reads a thread count of zero as "use your default", so a `hash_threads = 0` that were passed through would switch the bound off instead of setting it low. Counts above 1024 are refused for the same reason a percentage above 100 is — it is not a value anything can act on.
  - The run prints the count it is using — `Analysing for duplicates (4 threads)...` — so a `--threads` that did not take is visible rather than inferred.
  - **What this does not do:** it bounds the hashing phases only. Scanning, metadata extraction and the move phase are unchanged and still run one file at a time, so `--threads` will not speed those up. The measured benefit of any particular count on any particular device is not yet published; the benchmark corpus is page-cache-warm and so cannot answer that question — see [`docs/research/hashing-baseline.md`](docs/research/hashing-baseline.md).
- **[`docs/decisions/adr-007-parallel-hashing.md`](docs/decisions/adr-007-parallel-hashing.md) — why the duplicate scan hashes on several threads, and what had to be settled before it could.** Records that the output was not deterministic to begin with, so parallelising first would have made a real defect unfalsifiable — every "the output changed" report would have had two candidate causes and no way to tell them apart — and the two ordering rules that fixed it. Then: why flattening the candidate set mattered more than `par_iter` did (duplicate groups are usually pairs, so hashing *within* a group caps the whole cascade at two-way concurrency); why phase 2 buckets by `(size, digest)` and phase 3 by the digest alone; why there is no atomic skip counter; why the thread bound is a queue depth for the storage device rather than a use of the CPU, and why its default is capped at 8; why the pool is the run's own rather than `rayon`'s global one; and where the 64KB partial-hash promotion's boundary is. With the measured results — the cascade 102.49 ms → 39.174 ms (2.62×) on an 8-core M1 Pro — the reasons it is 2.62× and not 8×, the ten alternatives that were rejected, and the consequences, including that a re-run over an already-deduplicated library may keep a different copy than the first run did.
- **[`docs/decisions/adr-006-timezone-handling.md`](docs/decisions/adr-006-timezone-handling.md) — why a photograph is filed under its camera's own wall clock.** Records the three kinds of timestamp a file can carry (a naive wall clock, a wall clock with its own offset, and a bare instant) and why conflating them was the defect; the full resolution order for a file that stated no offset; why `nom-exif`'s resolved offset is the machine's own zone wearing the file's clothes and is therefore discarded; and why an IANA zone name is resolved per reading rather than once per run. With the alternatives that were rejected — keeping `DateTime<Utc>` and converting late, dropping the offset entirely, believing an Apple `creationdate` of exactly `+00:00`, and letting `--timezone` change which day a naive reading is filed under — and the consequences, including that this changes output paths with no migration.
- **[`docs/reference/format-support.md`](docs/reference/format-support.md) finalised.** Each ✅ and ❌ now names the test that establishes it, so the matrix can be checked against the suite rather than trusted; the RAW rows carry their second answer (a date read from an `.xmp` beside the file) in the table itself instead of only in a footnote; a **Sidecar dates** section states what that route does and will not do; and the page links ADR-006 rather than naming a file that did not exist when it was written.
- **[`docs/USER-GUIDE.md`](docs/USER-GUIDE.md) gains **Timezones**, **Sidecars** and **Refusing dates you do not trust**.** The timezone section leads with the user-visible rule — a frame taken at 23:30 is filed under that day on any machine — states the resolution order, and is explicit that `--timezone` does *not* move a wall-clock photograph to a different day but does move a filesystem-dated or container-clocked one. The sidecar section covers both naming conventions, why the convention is preserved rather than normalised, the two kinds of sidecar left in place, and the sidecar-derived date. The third covers `--require-exif`, why a refused file keeps its own name, and the summary's fallback warning. The options table gains `--timezone`, `--require-exif` and `--no-sidecars`; the preview-output section is brought up to date with the full tag set (`[SIDECAR]`, `[FS: UNREADABLE]`, `[FS: UNSUPPORTED]`, the `[tz:…]` markers and the indented sidecar lines), each explained.
- `README.md` distinguishes the thirty-two extensions that are **scanned** from the four container families a date can be **read out of**, names the sidecar and local-wall-clock behaviour, and lists `--timezone`, `--require-exif` and `--no-sidecars` among its examples.
- **XMP, AAE and THM sidecars now travel with the photograph they belong to.** A sidecar is bound to its parent by *filename* and nothing else — there is no identifier inside an `.xmp` naming the RAW file it describes — so a run that renamed `IMG_1234.CR2` and left `IMG_1234.xmp` where it was would silently detach every edit its owner had made. Both naming conventions are recognised, case-insensitively: `IMG_1234.xmp` beside `IMG_1234.CR2` (Adobe's, matched on the stem) and `IMG_1234.CR2.xmp` (darktable's, matched on the whole filename). **The convention is preserved rather than normalised** — a sidecar written the darktable way lands as `<new stem>.cr2.xmp` — because the tool that wrote it is the tool that will next go looking for it. A sidecar follows its parent wherever the parent actually landed, collision suffix included, and follows a duplicate into `duplicates/NNN/` too. It is never scanned as a media file: not counted in the scan totals, not deduplicated, not dated. Each sidecar move is journalled as its own entry, so `mmm undo` restores both files with no special case.
  - **What is left in place, and reported:** a sidecar with no media file of its name beside it, and one with *more* than one — `IMG_1234.xmp` beside both `IMG_1234.jpg` and `IMG_1234.dng` says nothing about which it belongs to, and attaching somebody's edits to the wrong photograph is a worse answer than refusing. Both are listed under `Sidecars left in place` with the reason, and counted in the summary as `Sidecars orphaned:`. They are **not** swept into `unsorted/`, which means "no usable date" and would say the wrong thing.
  - **Limits:** pairing is by filename alone — nothing inside a sidecar is consulted to decide which photograph it belongs to. (Its contents *are* now read for a date; see the XMP entry below.) Where the derived name is itself already taken, the sidecar takes a collision suffix of its own and the pair is broken; the journal records where it actually landed. A sidecar for a media file the scan never saw — one excluded by `skip_patterns` or by a narrowed extension list — is reported as an orphan, since from the run's point of view it has no parent.
- **A photograph with no readable date of its own now takes one from its XMP sidecar.** Reported as a new date source, `[SIDECAR]`, counted in the summary as `Date from XMP sidecar: N`. **This is the only way a TIFF-based RAW has ever been filed under the date it was taken** — no RAW container is one of the four this tool reads, so a `.cr2` library has until now been organised entirely by modification time while the answer sat in the text file beside every frame, which is exactly where darktable and Lightroom put it. Three properties are read, in order of how near each is defined to be to the shutter: `exif:DateTimeOriginal`, then `photoshop:DateCreated`, then `xmp:CreateDate` — the reverse of the order they are usually listed in, because `xmp:CreateDate` is the creation of the *resource*, and for a JPEG exported from a RAW five years later the resource was created five years later. A value that names the hour beats a higher-ranked one that names only a day, so an Adobe export's date-only `photoshop:DateCreated` does not file a photograph at midnight while the full timestamp sits in the same file. Both RDF serialisations are read — Adobe's attribute form and darktable's element form — and a property is recognised by its namespace URI under any prefix, falling back to the customary prefix when a file's `xmlns` declarations have been lost.
  - **What it will not do:** override a date the photograph itself recorded (the file is the primary witness; an editor that rewrites `xmp:CreateDate` on export must not silently re-file the original), read anything but a `.xmp` (an `.aae` is a binary property list and a `.thm` is a thumbnail), read GPS coordinates from the sidecar, or accept a date coarser than a whole day — `2024-03` would mean inventing the 1st of March, which nothing downstream could tell from a real one. A malformed sidecar is a warning and a skip; whatever was read before the damage is kept, and the run finishes normally.
  - **`--require-exif` admits a sidecar date.** The flag refuses filesystem timestamps, and an `xmp:CreateDate` is not one — it is a date somebody wrote down about the photograph, usually a verbatim copy of the EXIF tag relocated because a RAW file must never be written into. Excluding it would send an entire RAW library to `unsorted/` while the date sat beside every frame, defeating the flag for the people most likely to reach for it.
  - **A `[tz:sidecar]` timezone source** joins the existing four. An offset stated in a sidecar is believed like an EXIF `OffsetTimeOriginal`, and reported apart from it rather than as `[tz:exif]` — reporting an offset read from a text file as the file's own tag would be a small lie about the one thing that marker exists to be honest about. A sidecar date with no offset stays a bare wall clock and goes through `--timezone` and the rest of the resolution order, exactly as a naive `DateTimeOriginal` does.
  - New dependency: `quick-xml`, a streaming pull parser. Not an RDF stack — the whole question is three date properties out of one description, and a graph model would be brought in to answer it.
- **`--no-sidecars` and the matching `sidecars` config key** switch the whole thing off (the date as well as the move — the flag hands the scan an empty sidecar list, so there is no stage at which a sidecar exists to be read): sidecars are then not collected, not moved, not journalled and not reported, exactly as before this existed. `--no-sidecars=false` answers a configured `sidecars = false` from the command line.

An extension named both here and in `image` or `video` is treated as media, so a mistyped sidecar list can never stop photographs being organised.

- **The layout and the filenames are configurable: `date_directory_format`, `filename_format` and `include_location` now change the tree a run produces.**
  - **`date_directory_format`** is a strftime pattern for the dated directory, default `%Y-%m-%d` — one directory per day, which is what the organiser already produced. `"%Y/%m/%d"` restores the nested tree, `"%Y/%Y-%m"` files by year and month. A `/` in the pattern is a directory separator; everything else is a name.
  - **`filename_format`** is a token pattern for the filename, default `{date}-{time}{location}.{ext}` — unchanged from what the tool has always written. The tokens are `{date}` (`YYYY-MM-DD`), `{time}` (`HHMMSS`), `{location}`, `{ext}` and `{original_stem}`. `{location}` carries its own leading separator and expands to nothing when a file has no coordinates, so a file without one does not come out with a trailing `-`.
  - **`include_location = false`** drops the place name from every filename, and skips the geocoding lookup rather than performing it and discarding the result.

A mistyped `{stem}` is an error rather than five literal characters in the name of every file in the library.

  - **`--journal-dir <PATH>`** to relocate the journal, and **`--no-journal`** to disable it — refused together with `--commit` unless `--i-know-what-im-doing` is also passed, via the new `Config::validate()`. `Config::resolve_journal_dir()` returns `Option<PathBuf>` so "journalling is off" cannot be forgotten as a separate flag, and `config::journal_dir_for()` is the single definition of the layout shared by the writing and reading sides.
  - **`.mmm/` is excluded from scanning at any depth** (`METADATA_DIR_NAME` in `lib.rs`), so `mmm` never organises its own metadata. A `.mmm` named explicitly on the command line is still scanned.
  - **`organiser::MoveRecorder` and `MovePurpose`** own the record-then-move ordering in one place, rather than at every call site. A journal write failure stops the run; a move failure does not. `MoveRun` gains `journal_failed`, kept distinct from the operator's `stopped_early`.
  - **`reporter::JournalStatus`** (`NotNeeded` / `At(path)` / `Disabled`) plus the restore-outcome table and its labels. "No journal" means two opposite things — a preview that recorded nothing because it moved nothing, and a `--no-journal` run whose moves can never be put back — and only the second gets a warning. The journal path is printed twice, at open and in the summary, because an interrupted run never reaches its summary.
  - **`undo` exits non-zero whenever the library is not as it was** — any file skipped, any conflict, or any intent whose outcome the run never recorded. A conflicted file counts: it was restored, but not to the path it came from.
  - **An interrupted run's unresolved intents are reported, not ignored** — a `Possibly moved — verify manually` section naming both paths, with the destination flagged as the *planned* one, since the line that would have named where the file actually landed is exactly the line the interruption cost.
  - **An undo is itself journalled**, as a run of `Restore` intents committing as ordinary `MoveCommitted` records, so it is undoable with no third record type.
  - **`code/tests/undo.rs`** (7 integration tests) — full round trip byte-identical by BLAKE3 including nested subdirectories, round trip with duplicates, dry-run undo as a no-op, conflict on an occupied original path, a file modified after the run reported as skipped in both preview and commit, `journal list` newest-first, and a journal truncated mid-line still restoring exactly what it recorded. Every test drives two real processes rather than the library, because what only a process pair can prove is that the path the organiser wrote is the path undo goes looking for.
  - Dependencies added: `serde` (with `derive`) and `serde_json`. The run id's random suffix comes from the standard library's OS-seeded `RandomState`, so it costs no dependency.
- **Library target `mmm`** (`code/src/lib.rs`) re-exporting `config`, `error`, `geocoder`, `hasher`, `metadata`, `organiser`, `reporter` and `scanner`. Every module was previously private to `main.rs`, which made `tests/` integration tests structurally impossible. Both binaries now consume the library.
- **Offline fixture harness** (`code/tests/common/mod.rs`) — a `MediaTree` builder that synthesises byte-valid JPEGs carrying hand-built EXIF (`DateTimeOriginal`, `OffsetTimeOriginal`, and an optional GPS IFD with rational latitude/longitude and their `Ref` fields), plus `snapshot_tree`, `snapshot_tree_hashed` and `file_contents_by_marker` helpers for golden-tree assertions. No network access and no checked-in test assets.
- **Integration test suites** driving the real binary via `assert_cmd`:
  - `code/tests/fixture_selftest.rs` (6 tests) — proves the synthesised EXIF round-trips through `metadata::extract_metadata`, with a negative control so `DateSource::Exif` cannot pass vacuously.
  - `code/tests/organise.rs` (11 tests) — a default run leaves the input byte-identical; `--commit` files EXIF-dated JPEGs under `YYYY-MM-DD/`; GPS-tagged files gain the location suffix; non-media files are never touched; nested trees are traversed; an empty input exits cleanly with no output tree.
  - `code/tests/dedup.rs` (10 tests) — group formation, `duplicates/NNN/manifest.txt` contents, same-size-different-content files are not grouped, no duplicates means no `duplicates/` directory, and a BLAKE3 multiset conservation check proving no file is ever lost or invented.

Written before any of the fixes above, against the real `organiser` seams: an existing destination is never clobbered, a dangling symlink at the destination is never clobbered, a source deleted after planning errors rather than succeeding, a read-only destination errors naming the destination and leaves the source in place, and a same-size-but-corrupted cross-volume copy is detected without deleting the source (with a success twin proving a verified copy lands byte-identical).

### Fixed

- **A video with a corrupt location tag was named after a place nobody had been to.** `parse_iso6709` finished with two `f64::from_str` calls and returned whatever came out, and `f64::from_str` is not a coordinate validator: it accepts `NaN`, `inf` and `-inf` as words, and it accepts any magnitude, so `+302.2093` degrees of longitude parsed as readily as `+002.2093`. The reverse geocoder does not reject them either — measured, both `NaN` and infinity resolve to the *first record in the GeoNames dataset* (El Tarter, Andorra) — so the file was filed and renamed with a location that had been invented rather than read, and nothing in the output said so. A coordinate that is non-finite or outside ISO 6709's own bounds (latitude ±90, longitude ±180) is now refused, which puts the file back on the same path as a video carrying no location tag at all. Found by the new `parse_iso6709` fuzz target within seconds of it first being run; the crashing input is checked in as a regression seed.
- **Two documentation defects, found by checking the format matrix against the suite rather than reading it.** `docs/reference/format-support.md` marked MP4 GPS `✅ … — untested`, which is both answers in one cell; there is no fixture for the Android `moov/udta/©xyz` path, so it is now `⚠️ untested` like the other two unverified cells. `README.md` advertised "22 image + 11 video formats" against a built-in list of 21 image extensions.
- **BREAKING — a naive EXIF timestamp was read as UTC, so photographs were filed under the wrong day for anyone not on Greenwich.** `DateTimeOriginal` is a wall-clock reading with no zone in it — `2024:03:15 23:30:00` and nothing more — and `parse_date_string` called `and_utc()` on it. Downstream, the directory and the filename were then derived from that UTC instant, so a photo taken at half past eleven at night in Singapore landed in `2024-03-16/` and was renamed `2024-03-16-153000.jpg`. Every dated path now comes from the *local wall clock*: a naive reading is filed under exactly the digits the camera wrote, on every machine, and no code on the path to a destination converts to UTC. **This changes output paths.** A library organised by an earlier build from a machine not on UTC has files under the wrong dates and under filenames stamped with the wrong time; re-running does not migrate them, so `mmm undo` the old run if a journal exists for it, or move them yourself. Runs that were made on a UTC machine, and files that carry an `OffsetTimeOriginal` tag, are unaffected.
- **The same defect on the filesystem-fallback and video paths.** A filesystem timestamp and an MP4 `mvhd` creation time are genuine instants, but both were rendered in UTC before naming a directory. Both are now read against the resolved local zone.
- **BREAKING — an iPhone video's own recorded offset was thrown away, so `.mov` files were filed by the machine's distance from Greenwich.** `com.apple.quicktime.creationdate` is a string the phone writes with the offset it was standing in — `2024-03-15T23:30:00+08:00` — and it is the only thing in the file that knows where the camera was. The extractor converted it to a UTC instant and re-read it against the run's own zone, so the identical video filed under `2024-03-15-233000.mov` in Singapore and `2024-03-15-153000.mov` in London. That is the same defect this phase fixed for JPEG, surviving in the video path because the offset arrived already applied rather than in a separate tag. A recording's own offset is now believed, over `--timezone` and over the machine's zone, and reported as `[tz:exif]`. **This changes output paths** for `.mov` and `.mp4` files carrying an Apple `creationdate`, organised on a machine whose zone was not the one they were filmed in; re-running does not migrate them, so `mmm undo` the old run if a journal exists, or move them yourself. **Limit: a `creationdate` of exactly `+00:00` is still read as an instant.** The parser hands that over indistinguishably from the container's `mvhd` clock, which is always `+00:00`, and only a non-zero offset proves the file wrote it — so a video shot in the UTC zone can still lose its wall clock when the run's zone is not UTC. Recorded in [`docs/reference/format-support.md`](docs/reference/format-support.md).
- **`--timezone -05:30` was refused as an unknown flag `-0`.** Every offset west of Greenwich starts with a hyphen, so the flag worked for half the world and produced a usage error for the other half; the only spelling that got through was `--timezone=-05:30`. Both spellings are now accepted. Consequence of the fix: `--timezone` immediately followed by another flag takes that flag as its value, so `mmm --timezone --commit ~/Photos` fails with "`--commit` is not a timezone" rather than with a missing-value error.
- **`--timezone` typed before a subcommand was silently ignored.** `Cli::validate_placement` refuses an organise flag that lands where the named subcommand cannot act on it, and `--timezone` was missing from its list — so `mmm --timezone +08:00 undo ~/Photos` ran the undo with the flag quietly discarded, which is the exact failure that function exists to refuse. It is now named like the other settings flags. Found while adding `--require-exif` to the same list.

- **A global flag before a subcommand made the subcommand vanish: `mmm -v undo ~/Photos --commit` organised the library of somebody who had asked to put it back.** clap's `args_conflicts_with_subcommands` treats the top-level arguments as one group, and a `global = true` flag belongs to that group like any other — so once `-v`, `--config` or `--no-config` was seen, `undo`, `journal` and `config` were read as directory names for an organise run instead. With `--commit` also present that run moved files. The setting is removed; the refusal it was there for is now `Cli::validate_placement`, which names the misplaced flag instead of silently reinterpreting the command. **An organise flag typed before a subcommand is now an error** — `mmm --commit undo ~/Photos` says so rather than previewing and reporting success — except before `config`, which reports the settings flags rather than acting on them, and except `--dry-run`, which is a no-op wherever it lands. Affects every invocation since subcommands were introduced in this same unreleased cycle; no released version is affected.

Six further defects on the destructive path — every one of them able to lose a file — each fixed with a test written first that failed against the code as it stood. Rationale and platform detail in [`docs/decisions/adr-003-atomic-move-semantics.md`](docs/decisions/adr-003-atomic-move-semantics.md).

- **Overwrite-on-rename: a move could silently destroy the file already at its destination.** `resolve_collision` asked `Path::exists()` and then handed the path to `fs::rename`, which replaces whatever it finds. Two ways to lose a file: the gap between the check and the rename, and — with no race at all — a **dangling symlink**, which `exists()` follows and reports as absent. The move is now `fs::hard_link` + `remove_file`, and `link(2)` answers `EEXIST` for *anything* occupying the destination, dangling symlink included. `resolve_collision` is replaced by the pure `collision_candidate(path, attempt)`; `execute_move` walks candidates and lets the move itself be the sole authority on whether a name is free, so there is no stale answer to trust.
- **Cross-volume misclassification: every failed rename was treated as "must be a different volume"** and fell through to copy-and-delete, so a permission denial or a missing source surfaced to the operator as a temp-file copy error naming a path they never asked about. A failed link is now classified before it is acted on — `EXDEV` and "this filesystem has no hard links" take the copy path, and `EACCES`, `ENOENT`, `EROFS`, `ENOSPC` and everything else propagate with context naming both source and destination, with no copy attempted. `EPERM` and `EACCES` both arrive as `ErrorKind::PermissionDenied` and mean opposite things here, which is why the raw errno is consulted.
- **Size-only copy verification: a corrupted cross-volume copy passed and the source was then deleted.** `cross_volume_move` compared `metadata().len()`, so a copy off a failing drive or through a filesystem that substituted a block verified clean at the same length. The copy is now hashed with BLAKE3 as it is written and the landed file re-hashed, and the source is removed only once the two digests match. On a mismatch the temp file is removed, the source is untouched, and the error states both digests. Cleanup is a drop guard rather than six scattered `let _ = remove_file` calls, so no future early return can leave `.tmp-*` files accumulating in a photo library.
- **Manifest ordering: an interrupted dedup pass left duplicates relocated with no record of where they came from.** `move_duplicates` accumulated `manifest.txt` in a `String` and wrote it after the group's last move. `GroupManifest::create` now writes the header and the full intended source list — and `sync_data`s — *before* the group's first file moves, and appends and flushes each outcome line as it happens. Failed moves are recorded as `# FAILED:` lines with the full error chain instead of being dropped, and a manifest that cannot be written stops the group rather than relocating files unrecorded.
- **Scan and hash aborted the entire run on one unreadable file.** A single `0o000` directory returned no files at all — not even its readable siblings — and one unreadable file took down the whole dedup pass. `partial_hash` also called `read_exact` sized from scan-time metadata, which failed the run outright if a file shrank between the scan and the hash. `scan_directories` and `find_duplicates` are now infallible by signature: a bad entry is a warning and a skip, `partial_hash` reads from the open handle and treats a short read as an answer, and both skip counts appear in the summary as `Unreadable (scan):` and `Unhashable (dedup):` so silent omission is impossible.
- **Mid-run `process::exit(0)`: declining at a chunk prompt killed the process from inside a progress-bar closure**, skipping the summary and every destructor between there and `main`. Phase B is now `organiser::process_moves`, returning a `MoveRun` the summary consumes; stopping is a `break` carrying a value. Every planned file lands in exactly one count, and `Not processed:` reports the remainder. There is no `process::exit` left in `mmm`. Separately, `mmm dir --commit -c 0` panicked in `slice::chunks(0)`; a chunk size of zero now means one chunk holding everything.
- **Dated paths were not zero-padded, and derived filenames could contain path separators** — both found by the new property tests, neither reachable by any of the hand-written cases. Year `44` produced the directory `44/03/15` (`{}`, not `{:04}`), and a negative EXIF year — `-0044:03:15 10:00:00` parses, and real files carry dates like it — produced a top-level directory and a filename both beginning with `-`. A file extension arrives as arbitrary text and was pasted in verbatim, so an extension of `/` or `../..` put a separator in a filename and took the destination outside the output tree. Years are now formatted `{:04}`, a year outside `0..=9999` is rejected at `metadata::entry_to_datetime` so the existing filesystem-timestamp fallback gives the photo a real date, and the extension is sanitised through the shared `naming::sanitise_for_filename`.
- **Removed every panicking `expect()` from non-test code.** Four `ProgressStyle::…expect("valid template")` calls collapsed into a shared `hasher::styled_bar()` helper that falls back to the default bar — a cosmetic failure must never abort a run mid-move. `reporter::prompt_continue` now returns `false` on a failed stdout flush rather than panicking: if the prompt could not be shown, there is no consent to continue.
- Unchecked `as` casts in `hasher::partial_hash` replaced with `usize::try_from` / `i64::try_from` that propagate as errors.
- 68 clippy pedantic findings resolved rather than suppressed, including 8 missing `# Errors` doc sections. Three lints are allowed with written reasons in `Cargo.toml`.
- A dedup assertion that passed on APFS and failed on ext4 because it named the retained file rather than deriving it from scan order — caught by the new CI matrix on its first run.
- **Undo silently restored a file whose contents had changed, when the change kept the file's length.** An organise move was always journalled with `source_hash: null`, leaving undo only `source_size` to verify against — and a same-length edit passes a size check, so `mmm undo` moved the file back as though it were untouched. A file that reaches phase 3 of the dedup cascade is fully hashed to decide whether it is a duplicate, and that digest was being discarded. It now travels through `hasher::UniqueFile` into `PlannedMove::known_hash` and onto the intent line, so the retained original of a duplicate group and any file only phase 3 could prove unique are both journalled with a digest already paid for — no additional reads. Files eliminated in phase 1 or 2 are still recorded with `source_hash: null` and still verified by size alone; establishing a digest for those would mean fully reading every file in the library, which is the cost the cascade exists to avoid. `docs/architecture/journal-format.md` states which moves carry a digest and what the size-only fallback does not catch.

### Known issues

- `mmm-dedup-verifier` is vacuous against a tree `mmm` itself produced, and still exits 0. `move_duplicates` runs before the organise pass, so a finished `manifest.txt` records each original at its *input* path — which the organise pass then empties. The verifier finds nothing, confirms zero groups, prints "All verified groups are confirmed duplicates" and exits 0. Only `--check-originals` turns it into a failure. Pinned by a test that will fail loudly if the manifest is ever fixed.
- `duplicates/NNN` group numbering is not stable across runs — groups are accumulated by iterating a `HashMap`, whose ordering is randomly seeded per process. `duplicates/000/` is only reliable when the tree holds exactly one group.
- The dry-run listing is not a faithful preview of final filenames when two files resolve to the same destination. Collision suffixing (`-1`) happens in `execute_move`, not in `plan_move`.
- `unsorted/` is unreachable **without `--require-exif`**. `metadata::extract_metadata` falls back to the filesystem timestamp whenever no date can be read, and a file on disk always has one, so a bare run files an undateable photo under the date it was *written* rather than under `unsorted/`. `--require-exif` is the way to reach it, and is the reason the directory is no longer dead code; `DateSource::None` itself is still unreachable through the CLI.
- Timezone provenance is not yet derived from GPS coordinates. A photo carrying coordinates but no `OffsetTimeOriginal` tag falls through to `default_timezone` or the machine's zone like any other; `TimezoneSource::GpsDerived` is declared and nothing produces it. Filing is unaffected — a naive reading is filed under its own wall clock regardless — but the *instant* such a file is recorded at may be wrong by the difference between the two zones.
- Format coverage is verified per family against synthesised fixtures, and three cells of the matrix are not: `.cr3` (an ISO-BMFF container, but Canon writes a `CMT1` box rather than the HEIF `Exif` item, so it is unlikely to read), the Android `moov/udta/©xyz` GPS path, and GPS in a `.3gp`. Nothing is claimed about those either way. Verified working and verified *not* working are both listed in [`docs/reference/format-support.md`](docs/reference/format-support.md).
- No TIFF-based RAW is dated from the RAW itself — `nom-exif` reads four container families and none of them is a bare TIFF. An `.xmp` beside the file covers this for an edited library; a RAW library with no sidecars is dated from the filesystem unless `--require-exif` is passed.
- A file with GPS coordinates and no readable date loses its coordinates. The undated `FileMetadata` carrying them is discarded in favour of the filesystem timestamp, so the location never reaches the filename. Pre-existing rather than introduced; restoring it would change output filenames, so it is its own change.
